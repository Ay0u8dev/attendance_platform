# Backend Service Contracts

This document defines the currently implemented HTTP, WebSocket, and header contracts between services.

## 1) Shared Header Contract

### 1.1 Headers produced by auth validation

When `auth-service` validates a token successfully, it returns:

- `X-User-Id`: authenticated user id
- `X-User-Roles`: comma-separated roles
- `X-User-Email`: authenticated user email

These headers are injected by Traefik `forward-auth` into protected upstream HTTP requests.

### 1.2 Header used for trusted internal calls

`X-Request-Source` is used for service-to-service requests that bypass forwarded user headers.

Current trusted values:

- `auth-service`
- `attendance-service`
- `qr-service`
- `face-service`

## 2) JWT Contract (Auth-Service Issued Token)

The internal JWT generated by `auth-service` includes:

- `sub`: user email
- `iss`: configured issuer
- `id`: user id
- `email`: user email
- `roles`: list of role names
- `iat`
- `exp`

Validation checks include:

- subject must exist
- `email` claim must exist
- `sub` must match `email`
- `id` claim must exist
- `roles` must be non-empty
- issuer must match configured issuer when present

## 3) Auth Service

Base path: `/auth`

### `POST /auth/login`

Purpose:

- Accept Google `id_token`
- Validate with Google tokeninfo
- Verify allowed email domain
- Fetch existing user from `user-service`
- Return internal JWT access token

Request body:

```json
{
  "idToken": "google-id-token"
}
```

Success response:

```json
{
  "accessToken": "<internal-jwt>"
}
```

### `GET /auth/validate`

Purpose:

- Validate internal JWT
- Return identity/role headers for downstream services

Request headers:

- `Authorization: Bearer <internal-jwt>`

Success response:

- empty body
- response headers:
  - `X-User-Id`
  - `X-User-Roles`
  - `X-User-Email`

## 4) User Service

Base path: `/users`

### `POST /users/auth-user`

Purpose:

- Internal endpoint used by `auth-service`
- Returns existing user record

Required internal header:

- `X-Request-Source: auth-service`

### `GET /users/{id}`

Purpose:

- Admin-only user read endpoint

Required forwarded headers:

- `X-User-Id`
- `X-User-Roles`
- `X-User-Email`

Role requirement:

- `ADMIN`

### `GET /users/internal/students/roster`

Purpose:

- Internal endpoint used by `attendance-service`
- Returns a flat active-year roster for the provided group IDs

Required internal header:

- `X-Request-Source: attendance-service`

Query params:

- repeated `groupIds`

Success response:

```json
[
  {
    "studentId": 12,
    "groupId": 4,
    "firstName": "Aya",
    "lastName": "Bennani",
    "email": "aya.bennani@ump.ac.ma",
    "pfpUrl": "https://cdn.example.com/profiles/12.jpg",
    "numApogee": "22012345"
  }
]
```

Failure responses:

- `400`: missing or empty `groupIds`
- `401`: untrusted or missing request source
- `409`: zero or multiple active academic years

## 5) Attendance Service

Base path: `/attendance`

### 5.1 Teacher session lifecycle

#### `POST /attendance/sessions`

Purpose:

- Create one active attendance session for the authenticated teacher
- Load the active-year roster from `user-service`
- Persist the session header in `attendance_db`
- Initialize live session state in Redis with all students marked `UNKNOWN`

Required forwarded headers:

- `X-User-Id`
- `X-User-Roles`
- `X-User-Email`

Role requirement:

- `TEACHER`

Request body:

```json
{
  "groupIds": [1, 2],
  "courseLabel": "Distributed Systems",
  "roomLabel": "Room B12",
  "gpsLat": "34.6814",
  "gpsLon": "-1.9086",
  "method": "QR_CODE"
}
```

Success response:

```json
{
  "sessionId": 5,
  "teacherId": 77,
  "groupIds": [1, 2],
  "courseLabel": "Distributed Systems",
  "roomLabel": "Room B12",
  "gpsLat": "34.6814",
  "gpsLon": "-1.9086",
  "startedAt": "2026-04-27T10:00:00",
  "endsAt": "2026-04-27T10:30:00",
  "method": "QR_CODE",
  "status": "ACTIVE",
  "studentCount": 42
}
```

Failure responses:

- `400`: invalid request body
- `403`: caller lacks `TEACHER`
- `409`: teacher already has an active session
- `409`: roster lookup fails due to invalid academic year state
- `500`: live Redis initialization fails

Purpose:

Failure responses:

- `404`: no active session exists

#### `POST /attendance/sessions/{sessionId}/attendance`

Purpose:

- Teacher manually updates a student's attendance during an active session

Role requirement:

- `TEACHER`

Request body:

```json
{
  "studentId": 12,
  "status": "PRESENT"
}
```

Allowed manual statuses:

- `PRESENT`
- `ABSENT`

Success response:

```json
{
  "sessionId": 5,
  "studentId": 12,
  "status": "PRESENT",
  "markMethod": "MANUAL",
  "deviceId": null,
  "markedGpsLat": null,
  "markedGpsLon": null,
  "markedAt": "2026-04-28T12:00:00",
  "presentCount": 10,
  "absentCount": 1,
  "unknownCount": 31
}
```

Failure responses:

- `400`: invalid request body
- `403`: caller lacks `TEACHER` or does not own the session
- `404`: session or student not found in live state
- `409`: session is not active

#### `POST /attendance/sessions/{sessionId}/end`

Purpose:

- Finalize an active session
- Convert remaining `UNKNOWN` students to `ABSENT`
- Persist one final attendance record per student

Role requirement:

- `TEACHER`

Success response:

- same body shape as `GET /attendance/sessions/{sessionId}`
- `status = FINALIZED`
- `unknownCount = 0`

Finalization rules:

- unresolved `UNKNOWN` students become `ABSENT`
- final record GPS is persisted only for QR/FACE marks
- manual marks persist `markMethod = MANUAL` and leave GPS fields `null`
- aggregate snapshot fields are written onto the session header:
  - `presentCount`
  - `absentCount`
  - `unknownCount`
  - `endedAt`

Failure responses:

- `403`: caller lacks `TEACHER` or does not own the session
- `404`: session not found
- `409`: session is already finalized

### 5.2 Internal attendance updates

#### `POST /attendance/internal/sessions/{sessionId}/attendance`

Purpose:

- Internal update endpoint for QR and face services
- Updates live attendance state in Redis and broadcasts the teacher event
- `QR_CODE` remains student-device based
- `FACE_ID` is teacher-operated scanning via the teacher web client and `face-service`

Required internal header:

- `X-Request-Source: qr-service` or `X-Request-Source: face-service`

Request body:

```json
{
  "studentId": 12,
  "method": "FACE_ID",
  "deviceId": null,
  "gpsLat": null,
  "gpsLon": null
}
```

Rules:

- request source must be trusted
- `method` must match the request source
- `method` must match the session mode
- internal service updates always set `status = PRESENT`
- latest valid update wins across manual and internal service updates
- `QR_CODE`:
  - `deviceId` is required
  - `gpsLat` is required
  - `gpsLon` is required
  - one device may mark only one student within the same session
  - one student may use only one device within the same session
- `FACE_ID`:
  - `deviceId` may be `null`
  - `gpsLat` may be `null`
  - `gpsLon` may be `null`
  - device-binding rules do not apply
  - `face-service` validates the face match before calling `attendance-service`

Success response:

```json
{
  "sessionId": 5,
  "studentId": 12,
  "status": "PRESENT",
  "markMethod": "FACE_ID",
  "deviceId": null,
  "markedGpsLat": null,
  "markedGpsLon": null,
  "markedAt": "2026-04-28T12:01:00",
  "presentCount": 11,
  "absentCount": 0,
  "unknownCount": 31
}
```

Failure responses:

- `400`: invalid request body
- `400`: `QR_CODE` request is missing `deviceId`
- `400`: `QR_CODE` request is missing GPS coordinates
- `401`: missing or untrusted internal source
- `404`: session or student not found in live state
- `409`: session is not active
- `409`: request source does not match attendance method
- `409`: attendance method does not match session mode
- `409`: `QR_CODE` device is already used by another student in this session
- `409`: `QR_CODE` student is already bound to another device in this session

## 6) Attendance WebSocket Contract

Handshake endpoint:

- `/attendance/ws`

STOMP `CONNECT` requirements:

- `Authorization: Bearer <jwt>` native header is required
- token is validated by `attendance-service` through `auth-service /auth/validate`

Subscription destination:

- `/topic/attendance.sessions.{sessionId}`

Subscription rules:

- allowed for the owning teacher of the session
- allowed for admins
- denied for students
- denied for other teachers
- denied for anonymous clients

### Event: `ATTENDANCE_UPDATED`

```json
{
  "eventType": "ATTENDANCE_UPDATED",
  "sessionId": 5,
  "studentId": 12,
  "status": "PRESENT",
  "markMethod": "QR_CODE",
  "deviceId": "scanner-entrance-01",
  "markedGpsLat": "34.6820",
  "markedGpsLon": "-1.9091",
  "markedAt": "2026-04-28T12:01:00",
  "presentCount": 11,
  "absentCount": 0,
  "unknownCount": 31
}
```

### Event: `SESSION_FINALIZED`

```json
{
  "eventType": "SESSION_FINALIZED",
  "sessionId": 5,
  "status": "FINALIZED",
  "presentCount": 11,
  "absentCount": 31,
  "unknownCount": 0
}
```

## 7) Notes on Error Shapes

Current behavior is improved but not perfectly standardized across all services:

- attendance-service uses structured JSON for application errors
- some auth validation failures still return plain text
- user-service still uses servlet `sendError` in some paths

That inconsistency is real technical debt. It is not fixed by pretending otherwise in the docs.
