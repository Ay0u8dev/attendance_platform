# Backend Service Contracts

This document defines the currently implemented HTTP contracts and header contracts between services.

Bootstrap ownership note:

- `attendance-service` is the intended owner of session lifecycle and attendance persistence for the merged attendance flow.
- `attendance-service` now exposes the first session creation contract and owns live session initialization.

## 1) Shared Header Contract

### 1.1 Headers produced by auth validation

When `auth-service` validates a token successfully, it returns:

- `X-User-Id`: authenticated user id
- `X-User-Roles`: comma-separated roles (example: `ADMIN,USER`)
- `X-User-Email`: authenticated user email

These headers are injected by Traefik (`forward-auth`) into protected upstream requests.

### 1.2 Header used for trusted internal calls

- `X-Request-Source: auth-service`

`user-service` currently bypasses role/header checks for requests carrying this exact source value.

## 2) JWT Contract (Auth-Service Issued Token)

The internal JWT generated by `auth-service` includes:

- `sub`: user email
- `iss`: `auth-service` (or configured issuer)
- `id`: user id
- `email`: user email
- `roles`: list of role names
- `iat`, `exp`

Validation checks include:

- Subject must exist
- `email` claim must exist
- `sub` must match `email`
- `id` claim must exist
- `roles` must be non-empty
- issuer must match configured issuer (if present)

## 3) Endpoint Contracts

## 3.1 Auth Service

Base path: `/auth`

### `POST /auth/login`

Purpose:

- Accept Google `id_token`
- Validate with Google tokeninfo
- Verify allowed email domain
- Fetch existing user from `user-service`
- Return internal JWT access token

Request body:

```json
{
  "idToken": "google-id-token"
}
```

Success response (`200 OK`):

```json
{
  "accessToken": "<internal-jwt>"
}
```

Typical failure responses:

- `400`: missing `idToken`
- `401`: authentication failure
- `403`: unauthorized domain or disabled account

Example:

```bash
curl -X POST http://localhost/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"idToken":"<google-id-token>"}'
```

### `GET /auth/validate`

Purpose:

- Validate internal JWT
- Return identity/role headers for downstream services

Request headers:

- `Authorization: Bearer <internal-jwt>`

Success response (`200 OK`):

- Empty body
- Response headers include:
  - `X-User-Id`
  - `X-User-Roles`
  - `X-User-Email`

Failure response (`401 Unauthorized`):

- Plain text message (current behavior)

Example:

```bash
curl -i http://localhost:8081/auth/validate \
  -H "Authorization: Bearer <internal-jwt>"
```

## 3.2 User Service

Base path: `/users`

### `POST /users/auth-user`

Purpose:

- Internal endpoint used by `auth-service` login flow
- Returns existing user record
- On first login, updates `firstLogin=false` and `pfpUrl`

Request headers:

- `X-Request-Source: auth-service`

Request body:

```json
{
  "email": "user@ump.ac.ma",
  "pfpUrl": "https://example.com/avatar.jpg"
}
```

Success response (`200 OK`):

- Returns user entity JSON (includes id, email, roles, enabled, firstLogin, and other entity fields)

Failure responses:

- `400`: email missing
- `404`: user not found

Direct internal example:

```bash
curl -X POST http://localhost:8082/users/auth-user \
  -H "Content-Type: application/json" \
  -H "X-Request-Source: auth-service" \
  -d '{"email":"user@ump.ac.ma","pfpUrl":"https://example.com/avatar.jpg"}'
```

### `GET /users/{id}`

Purpose:

- Retrieve user information
- Requires `ADMIN` role (`@RequireRole({"ADMIN"})`)

Required forwarded headers:

- `X-User-Id`
- `X-User-Roles`
- `X-User-Email` (optional for check, useful for context)

Success response (`200 OK`):

```json
{
  "email": "ayoubelebbar@ump.ac.ma",
  "firstName": "Ayoub",
  "lastName": "Elebbar",
  "pfpUrl": "...",
  "roles": ["ADMIN"],
  "enabled": true,
  "firstLogin": false
}
```

Failure responses:

- `401`: missing auth headers
- `403`: insufficient roles
- `404`: user not found

Gateway example (recommended):

```bash
curl http://localhost/api/users/1 \
  -H "Authorization: Bearer <internal-jwt>"
```

## 4) Inter-Service Call Contract (Auth -> User)

Current implemented call:

- Caller: `auth-service`
- Client type: OpenFeign
- Target: `${services.user-service.url}/users/auth-user`
- Header injected automatically: `X-Request-Source: auth-service`
- Body fields sent: `email`, `pfpUrl`

Expected behavior:

- `user-service` must return an existing user for valid domain accounts.
- `auth-service` expects fields at least compatible with:
  - `id`
  - `email`
  - `roles`
  - `enabled`
  - `firstLogin`

## 4.1 Inter-Service Call Contract (Attendance -> User)

Current implemented call:

- Caller: `attendance-service`
- Client type: OpenFeign
- Target: `${services.user-service.url}/users/internal/students/roster`
- Header required: `X-Request-Source: attendance-service`
- Query params: repeated `groupIds`

### `GET /users/internal/students/roster`

Purpose:

- Internal endpoint used by `attendance-service`
- Returns a flat active-year roster for the provided group IDs

Request headers:

- `X-Request-Source: attendance-service`

Request query:

- `groupIds`: one or more group identifiers

Success response (`200 OK`):

```json
[
  {
    "studentId": 12,
    "groupId": 4,
    "firstName": "Aya",
    "lastName": "Bennani",
    "email": "aya.bennani@ump.ac.ma",
    "numApogee": "22012345"
  }
]
```

Failure responses:

- `400`: missing or empty `groupIds`
- `401`: untrusted or missing request source
- `409`: zero or multiple active academic years

## 4.2 Attendance Service

Base path: `/attendance`

### `POST /attendance/sessions`

Purpose:

- Create one active attendance session for the authenticated teacher
- Load the active-year roster from `user-service`
- Persist the session header in `attendance_db`
- Initialize live session state in Redis with all students marked `UNKNOWN`

Required forwarded headers:

- `X-User-Id`
- `X-User-Roles`
- `X-User-Email`

Role requirement:

- `TEACHER`

Request body:

```json
{
  "groupIds": [1, 2],
  "courseLabel": "Distributed Systems",
  "roomLabel": "Room B12",
  "gpsLat": "34.6814",
  "gpsLon": "-1.9086",
  "method": "QR_CODE"
}
```

`method` enum values currently supported:

- `QR_CODE`
- `FACE_ID`
- `MANUAL`

Success response (`200 OK`):

```json
{
  "sessionId": 5,
  "teacherId": 77,
  "groupIds": [1, 2],
  "courseLabel": "Distributed Systems",
  "roomLabel": "Room B12",
  "gpsLat": "34.6814",
  "gpsLon": "-1.9086",
  "startedAt": "2026-04-27T10:00:00",
  "endsAt": "2026-04-27T10:30:00",
  "method": "QR_CODE",
  "status": "ACTIVE",
  "studentCount": 42
}
```

Failure responses:

- `400`: invalid request body
- `403`: caller lacks `TEACHER`
- `409`: teacher already has an active session
- `409`: roster lookup fails due to invalid academic year state
- `500`: live Redis initialization fails

### `POST /attendance/sessions/{sessionId}/attendance`

Purpose:

- Teacher manually updates a student's attendance during an active session
- Manual updates are allowed even when the session mode is `QR_CODE` or `FACE_ID`

Required forwarded headers:

- `X-User-Id`
- `X-User-Roles`
- `X-User-Email`

Role requirement:

- `TEACHER`

Request body:

```json
{
  "studentId": 12,
  "status": "PRESENT"
}
```

Allowed `status` values for manual updates:

- `PRESENT`
- `ABSENT`

Success response (`200 OK`):

```json
{
  "sessionId": 5,
  "studentId": 12,
  "status": "PRESENT",
  "markMethod": "MANUAL",
  "deviceId": null,
  "markedGpsLat": null,
  "markedGpsLon": null,
  "markedAt": "2026-04-28T12:00:00",
  "presentCount": 10,
  "absentCount": 1,
  "unknownCount": 31
}
```

Failure responses:

- `400`: invalid request body
- `403`: caller lacks `TEACHER` or does not own the session
- `404`: session or student not found in live state
- `409`: session is not active

### `POST /attendance/internal/sessions/{sessionId}/attendance`

Purpose:

- Internal update endpoint for QR and face services
- Updates live attendance state in Redis and broadcasts the teacher event

Request headers:

- `X-Request-Source: qr-service` or `X-Request-Source: face-service`

Request body:

```json
{
  "studentId": 12,
  "method": "QR_CODE",
  "deviceId": "scanner-entrance-01",
  "gpsLat": "34.6820",
  "gpsLon": "-1.9091"
}
```

Rules:

- request source must be trusted
- `method` must match the request source
- `method` must match the session mode
- QR and FACE marks must include GPS coordinates
- one device may mark only one student within the same session
- one student may use only one device within the same session
- self-service updates always set `status = PRESENT`
- latest valid update wins across manual and self-service changes

Success response (`200 OK`):

```json
{
  "sessionId": 5,
  "studentId": 12,
  "status": "PRESENT",
  "markMethod": "QR_CODE",
  "deviceId": "scanner-entrance-01",
  "markedGpsLat": "34.6820",
  "markedGpsLon": "-1.9091",
  "markedAt": "2026-04-28T12:01:00",
  "presentCount": 11,
  "absentCount": 0,
  "unknownCount": 31
}
```

Failure responses:

- `400`: invalid request body
- `401`: missing or untrusted internal source
- `404`: session or student not found in live state
- `409`: session is not active
- `409`: request source does not match attendance method
- `409`: attendance method does not match session mode
- `409`: device is already used by another student in this session
- `409`: student is already bound to another device in this session

### `GET /attendance/sessions/{sessionId}`

Purpose:

- Hydrate the teacher session screen after refresh or reconnect
- Return live Redis state while the session is active
- Return persisted DB state after the session is finalized

Required forwarded headers:

- `X-User-Id`
- `X-User-Roles`
- `X-User-Email`

Role requirement:

- `TEACHER`

Success response (`200 OK`):

```json
{
  "sessionId": 5,
  "teacherId": 77,
  "groupIds": [1, 2],
  "courseLabel": "Distributed Systems",
  "roomLabel": "Room B12",
  "gpsLat": "34.6814",
  "gpsLon": "-1.9086",
  "startedAt": "2026-04-28T12:00:00",
  "endsAt": "2026-04-28T12:30:00",
  "method": "QR_CODE",
  "status": "ACTIVE",
  "presentCount": 11,
  "absentCount": 0,
  "unknownCount": 31,
  "students": [
    {
      "studentId": 12,
      "groupId": 1,
      "firstName": "Aya",
      "lastName": "Bennani",
      "email": "aya.bennani@ump.ac.ma",
      "numApogee": "22012345",
      "status": "PRESENT",
      "markMethod": "QR_CODE",
      "deviceId": "scanner-entrance-01",
      "markedGpsLat": "34.6820",
      "markedGpsLon": "-1.9091",
      "markedAt": "2026-04-28T12:01:00"
    }
  ]
}
```

Failure responses:

- `403`: caller lacks `TEACHER`
- `404`: session not found

### `POST /attendance/sessions/{sessionId}/end`

Purpose:

- Finalize an active session
- Convert remaining `UNKNOWN` students to `ABSENT`
- Persist one final attendance record per student
- Keep finalized Redis state briefly for post-end readback

Required forwarded headers:

- `X-User-Id`
- `X-User-Roles`
- `X-User-Email`

Role requirement:

- `TEACHER`

Success response (`200 OK`):

- Same shape as `GET /attendance/sessions/{sessionId}`
- `status = FINALIZED`
- `unknownCount = 0`

Finalization rules:

- unresolved `UNKNOWN` live students become `ABSENT`
- QR/FACE marks persist `deviceId`, `markedGpsLat`, and `markedGpsLon`
- manual marks persist `markMethod = MANUAL` with GPS fields left `null`
- finalized Redis state is retained temporarily with TTL for UI readback
- repeated finalization attempts are rejected after the session is already finalized

Failure responses:

- `403`: caller lacks `TEACHER` or does not own the session
- `404`: session not found
- `409`: session is already finalized

## 5) Notes on Response Shapes

Current behavior is partially consistent but not fully standardized:

- Some auth errors return structured JSON (`status`, `message`)
- Some auth validation failures return plain text
- user-service returns plain text for some errors via servlet `sendError`

For new endpoints, follow the target error standard in `backend/docs/backend-service-rules.md`.
